## Objective

Make `super-chat` the complete, embeddable chat application used by
`obsidian-ai`, `arxivite`, and a future standalone shell.

Host products provide data and platform capabilities. They must not own or
reimplement chat mechanics such as session orchestration, streaming, tool-call
state, approval UI, agent loops, message rendering, context budgeting, or RAG
coordination.

The target integration should be conceptually this small:

```tsx
<SuperChatApp host={productHost} />
```

```text
super-chat application
  - owns all reusable chat mechanics and chat UI
  - consumes neutral, capability-based host contracts
  - runs with a fixture host in an ordinary browser

  - runs inside arxivite through an Arxivite host
  - can run in a standalone shell through a desktop/mobile host
```

## Non-Goals

- Do not import Obsidian, Supabase, Electron, or Capacitor APIs into the core.
- Do not pass large product objects such as an Obsidian `App` or raw Supabase
  client through the host contract.
- Do not copy all of `obsidian-ai` into this repository wholesale.
- Do not make every capability mandatory for every host.
- Do not flip Arxivite's feature toggle or delete its legacy path before the
  new host integration passes acceptance.

## Message Context Plan — 2026-09-07

The first message-context extraction follows
[`implementation-details/model-history-and-context.md`](../implementation-details/model-history-and-context.md).
It must preserve every tool call and result, use the provider conversion
already proven in `obsidian-ai`, and keep the existing token estimate. The
full result remains available to storage and display; the copy sent in the
next provider request may be shortened when needed. Advanced context
selection and compaction are not required until a real problem justifies
them.

## Remote Conversation Boundary — 2026-09-07

The first harness requirement is inter-user conversation between separate
product instances. This adds an optional, harness-neutral messaging capability
to the host contract; it does not make super-chat responsible for Arxivite
routing, user directories, or a particular network transport.

- The host supplies authenticated sender identity, conversation membership, and
  a send/subscribe transport for a shared conversation.
- Super-chat owns the message envelope, sender attribution, inbound-message
  lifecycle, persistence integration, duplicate handling, ordering, and
  reconnect/replay behavior.
- An external conversation identity maps a host conversation to one shared
  super-chat session without replacing the engine-owned session ID.
- Polling, WebSockets, Supabase Realtime, presence, typing indicators, and
  read receipts are host/product decisions and are not required for this
  first shared slice.

The first fixture acceptance should use two clients and prove authenticated
send, inbound delivery, reload/reconnect replay, duplicate suppression, and
unauthorized membership rejection. Arxivite-specific routing remains in the
Arxivite host work tracked by T19 and its T32/T78 records.

## Acceptance Criteria

- [ ] `SuperChatApp` is the complete chat application for a fixture host.
- [x] Tool execution is fail-closed unless `autoApply` explicitly permits it.
- [x] Manual approval can pause, approve, reject, cancel, and resume a turn.
- [ ] The engine owns session/message lifecycle; hosts only provide storage
      operations and product data.
- [ ] Agentic RAG/context options have real shared behavior or are removed
      from the contract.
- [ ] Agentic retrieval uses shared tools and evidence rather than host-owned
      intent routing or a completed host RAG answer.
- [ ] One read and one write capability pass the same contract tests for the
      fixture, Obsidian, and Arxivite hosts.
- [ ] Arxivite contains no product-owned streaming or tool-event loop in its
      final integration path.
- [ ] A response with several tool calls preserves every call and its result
      in valid message context after reload.
- [ ] An optional host messaging capability can deliver a human message to a
      second client while preserving sender identity, ordering, and replay.
- [ ] A tool result that is too large can be shortened for the next provider
      request without losing the complete saved result; an unfit newest result
      produces a clear recoverable error.
- [ ] Obsidian-specific behavior remains in the Obsidian host/plugin layer.
- [ ] Clean package builds pass in `super-chat`, `obsidian-ai`, and `arxivite`.
- [ ] Migration, compatibility, and rollback notes are documented.

## 2026-09-01 Phase 5 Plan Verification

The former Phase 5 review described a thin host-backed retrieval improvement path.
That plan is superseded by the approved agentic-runtime direction: retrieval
must be driven by the shared tool-calling loop and structured evidence.
The first implementation slice must move retrieval inside the `ChatEngine`
turn lock and persistence/cancellation/failure lifecycle. Retrieval currently
runs before those protections are active.

The recommended Phase 5 core changes are:

- settle one neutral retrieval/result/error contract and the compatibility
  treatment for legacy paper-oriented RAG methods;
- add a small pure retrieval/context module for source validation,
  deduplication, ordering, size-limited context assembly, and untrusted-evidence
  formatting;
- pass abort signals and request limits through `HostRAGAdapter`;
- persist size-limited retrieval context and provenance with safe migration/replay;
- wire retrieval progress, errors, and source state into the shared React path;
- extract reusable agentic retrieval behavior from obsidian-ai into super-chat;
  hosts retain indexes, document access, domain data, and handlers.

The review found no need for a new persistence manager, `AgentLoop` changes, a
large RAG manager, or an inline-citation parser. It also found a timing-sensitive
`SuperChatApp` test under full-suite parallel load (121/122 in that run; the
isolated test passed), which must be stabilized before the Phase 5 acceptance
gate.

## 2026-09-01 Phase 5 Lifecycle Slice

T16 implemented the first shared-core improvement slice. Retrieval now begins
only after the engine has established the active-turn lock and persisted the
user turn, receives the engine abort signal through the host adapter, and
records retrieval success, failure, or cancellation in the durable turn
record. Slow retrieval cannot hold the stream open after cancellation because
the engine races the host promise against the active signal.

## 2026-09-07 Route-safe Application Initialization

`SuperChatApp` now supports an optional stable cache key for embedders that
retain a host-backed engine across route unmounts. Engine creation is no longer

evicts failed cached initializations for retry. Hosts without a cache key retain
the existing per-mount lifecycle.
