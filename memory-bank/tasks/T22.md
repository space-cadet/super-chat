## Objective

Make `super-chat` the complete, embeddable chat application used by
`obsidian-ai`, `arxivite`, and a future standalone shell.

Host products provide data and platform capabilities. They must not own or
reimplement chat mechanics such as session orchestration, streaming, tool-call
state, approval UI, agent loops, message rendering, context budgeting, or RAG
coordination.

The target integration should be conceptually this small:

```tsx
<SuperChatApp host={productHost} />
```

## Authoritative Design

See
[`implementation-details/embeddable-super-chat-platform.md`](../implementation-details/embeddable-super-chat-platform.md).
That document defines ownership, contracts, migration phases, safety rules,

## Required Outcome

```text
super-chat application
  - owns all reusable chat mechanics and chat UI
  - consumes neutral, capability-based host contracts
  - runs with a fixture host in an ordinary browser
  - runs inside obsidian-ai through an Obsidian host
  - runs inside arxivite through an Arxivite host
  - can run in a standalone shell through a desktop/mobile host
```

## Workstreams

1. **Core contract and safety**
   - Define `SuperChatHost` as optional capabilities, not product objects.
   - Make missing tool approval fail closed.
   - Connect engine approval state to React UI.
   - Replace polling with an observable engine state/event contract.
   - Define durable external session identity and one persistence owner.
   - Decide and implement the shared RAG/context orchestration boundary.

2. **Obsidian capability extraction (T15)**
   - Use `obsidian-ai` as the behavioral reference.
   - Move only reusable chat mechanics into `super-chat`.
   - Preserve Obsidian-specific vault, editor, workspace, plugin, sync, and
     lifecycle behavior behind host capabilities.

3. **Obsidian host migration (T18)**
   - Implement an `ObsidianSuperChatHost`.
   - Migrate one vertical slice at a time with behavior-preserving tests.
   - Keep the existing plugin usable throughout the migration.

4. **Arxivite harness migration (T19)**
   - Replace Arxivite-owned chat mechanics with `SuperChatApp`.
   - Keep Arxivite as the source of identity, papers, bookmarks, Supabase
     persistence, research retrieval, product tools, and navigation.
   - Remove the legacy path only after end-to-end acceptance.

5. **Distribution and compatibility (T21)**
   - Establish versioned releases and compatibility checks.
   - Remove source-versus-`dist` ambiguity and stale submodule consumption.
   - Test clean installs with each host's dependency environment.

## Implementation Order

3. T15 first reusable capability extraction from `obsidian-ai`.

5. T19 Arxivite migration to `SuperChatApp` plus `ArxiviteSuperChatHost`.
6. T21 versioned release and cross-host clean-install matrix.
7. Standalone desktop host; mobile host work follows desktop acceptance.

## Non-Goals

- Do not import Obsidian, Supabase, Electron, or Capacitor APIs into the core.
- Do not pass large product objects such as an Obsidian `App` or raw Supabase
  client through the host contract.
- Do not copy all of `obsidian-ai` into this repository wholesale.
- Do not make every capability mandatory for every host.
- Do not flip Arxivite's feature toggle or delete its legacy path before the
  new host integration passes acceptance.

## Acceptance Criteria

- [ ] `SuperChatApp` is the complete chat surface for a fixture host.
- [x] Tool execution is fail-closed unless `autoApply` explicitly permits it.
- [x] Manual approval can pause, approve, reject, cancel, and resume a turn.
- [ ] The engine owns session/message lifecycle; hosts only provide storage
      operations and product data.
- [ ] RAG/context options have real behavior or are removed from the contract.
- [ ] One read and one write capability pass the same contract tests for the
      fixture, Obsidian, and Arxivite hosts.
- [ ] Arxivite contains no product-owned streaming or tool-event loop in its
      final integration path.
- [ ] Obsidian-specific behavior remains in the Obsidian host/plugin layer.
- [ ] Clean package builds pass in `super-chat`, `obsidian-ai`, and `arxivite`.
- [ ] Migration, compatibility, and rollback notes are documented.

## 2026-09-01 Phase 5 Plan Verification

The Sol-medium read-only review confirmed that the Phase 5 direction is sound,
but refined the work into a hardening sequence for the Phase 4 retrieval path.
The first implementation slice must move retrieval inside the `ChatEngine`
turn lock and persistence/cancellation/failure lifecycle. Retrieval currently
runs before those protections are active.

The recommended Phase 5 core changes are:

- settle one neutral retrieval/result/error contract and the compatibility
  treatment for legacy paper-oriented RAG methods;
- add a small pure retrieval/context module for source validation,
  deduplication, ordering, bounded context assembly, and untrusted-evidence
  formatting;
- pass abort signals and request limits through `HostRAGAdapter`;
- persist bounded retrieval context and provenance with safe migration/replay;
- wire retrieval progress, errors, and source state into the shared React path;
- keep Arxivite ranking/PocketFlow and Obsidian search host-owned.

The review found no need for a new persistence manager, `AgentLoop` changes, a
large RAG manager, or an inline-citation parser. It also found a timing-sensitive
`SuperChatApp` test under full-suite parallel load (121/122 in that run; the
isolated test passed), which must be stabilized before the Phase 5 acceptance
gate.

## 2026-09-01 Phase 5 Lifecycle Slice

T16 implemented the first shared-core hardening slice. Retrieval now begins
only after the engine has established the active-turn lock and persisted the
user turn, receives the engine abort signal through the host adapter, and
records retrieval success, failure, or cancellation in the durable turn
record. Slow retrieval cannot hold the stream open after cancellation because
the engine races the host promise against the active signal.

Verification passed: TypeScript, 13 test files / 124 tests, pinned package
ESM/CJS/declaration build, and `git diff --check`.

The bounded retrieval/context slice is now implemented. The pure helper
validates source/provenance fields, deduplicates and orders results, applies
result and context limits, formats evidence as untrusted reference material,
and stores the bounded context on the durable turn. Product migrations remain
deferred.

The next Phase 5 slice is normalized retrieval result/error handling,
partial/warning outcomes, replay behavior, and shared React retrieval state.
