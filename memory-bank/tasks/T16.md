## Objective

Make RAG a real shared chat workflow: `super-chat` owns retrieval
orchestration, context budgeting, progress, citations, provenance, and replay;
each host owns its data source, retrieval algorithm, and domain ranking.

Do not port Arxivite's domain-specific RAG implementation into `super-chat`.
Keep it in Arxivite behind `RetrievalCapability`.

## Shared Flow

```text
user turn
  -> shared retrieval decision
  -> host retrieval capability
  -> normalized sources with stable IDs and provenance
  -> shared budgeting and prompt assembly
  -> shared progress/citation events
  -> persisted record for replay
```

## Work

- [ ] Reconcile existing `RAGAdapter`, `ContextAdapter`, and `enableRAG` types.
- [ ] Define normalized retrieval request, source, provenance, and error types.
- [ ] Define cancellation, authorization, and partial-result behavior.
- [ ] Integrate retrieval into `ChatEngine.sendMessage()` or remove misleading

- [ ] Add fixture retrieval with one cited result.
- [ ] Apply shared contract tests to Arxivite's retrieval capability.
- [ ] Add Obsidian/local-document retrieval only as separate host work.

## Arxivite Ownership

Arxivite retains its intent classifier, PocketFlow pipeline, Supabase/PDF
storage, paper filtering, ranking, and anti-hallucination domain prompts where
appropriate. It returns normalized results; it does not own the chat event
loop or citation UI.

## Completion Criteria

- Enabling RAG changes the actual turn pipeline.
- Retrieval progress and citations are rendered by shared UI.
- Provenance survives persistence and reload.
- Arxivite's domain RAG remains inside Arxivite.
